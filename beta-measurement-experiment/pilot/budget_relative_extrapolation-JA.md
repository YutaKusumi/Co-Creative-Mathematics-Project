# 計算予算の相対外挿 ―― 0.6B 実測錨 → 1.7B / 4B / 8B（粗見積り）

*β測定実験・パイロット／台帳 #10「計算予算の実数見積り」の run数前段。2026-06-12。*

> **地位の明示：** 本ノートは**単一の実測錨**（Qwen3-0.6B・L4・[pilot_0p6B_summary.txt](pilot_0p6B_summary.txt)）からの**外挿**である。
> 1.7B/4B/8B の t_run は**未測定**。各モデルは自前のパイロットで t_run を確かめてから本走する
> （0.6B は「走れることの確認」だけで版依存バグ 2 件を出した ―― 外挿は測定の代わりにならない）。
> 禁制4（規模を外挿しない）に抵触しないのは、これを**確定値でなく予算planの粗見積り**として
> 明示ラベルし、各規模で実測 t_run に置換する前提だからである。

## 1. 実測錨（置換しない正典）

| 量 | 実測値（Qwen3-0.6B・NVIDIA L4・4-bit QLoRA+DPO・SEQ1024・実効batch16・rank16） |
|---|---|
| 1ステップ計算時間（中央） | **6.795 s** |
| 1 checkpoint 保存 I/O | 0.72 s |
| 1 checkpoint 容量 | 31.7 MB |
| 代表 run（300step+60save） | **34.7 分 = 0.578 GPU時間** |

## 2. 外挿の方法と仮定（隠さず）

**第一近似：1ステップ時間 ∝ 非埋め込みパラメータ数 N。** 根拠 ―― QLoRA の per-step 計算は
凍結 4-bit ベースの forward+backward（≈4N FLOPs/token）が支配し、tokens/step（=実効batch×系列長=16384）は
規模不変ゆえ、計算は N に比例する（帯域律速の領域でも重み読込∝N で同傾向）。

**この第一近似を上下に動かす三つの補正（互いに部分相殺）：**
- **↑ 非埋め込みで測ると小型ほど埋め込み（安価）比率が高い** ―― 総paramでなく層paramで測ると比は大きくなる。
- **↓ 固定オーバヘッド**（Python・kernel launch・LoRA optimizer・dequant 準備）は N に依らず、6.795s に含まれる
  ―― 純線形は大型を過大評価する（小型ほどオーバヘッド比率が高いため）。
- **↓ GPU 利用率**は大型ほど改善（小型は latency 律速で L4 を使い切らない）―― 大型の time/param は逓減。

正味、**純・総param線形を中心に ±約 0.7–1.3× の帯**で見るのが正直（単一錨・13× 外挿ゆえ広い）。
保存 I/O は LoRA アダプタ容量（rank 固定で N に緩く依存）ゆえ数秒以内に留まり、予算寄与は 0.6B で 2%＝**非支配**。

## 3. 外挿表（総param線形・中心値／帯）

総param比（対 0.6B）：1.7B=2.83× / 4B=6.67× / 8B=13.3×。代表 run=300step+60save、保存寄与 ~2% 加算。

| モデル | 1step（中心） | 1 run 中心 | 1 run 帯（×0.7–1.3） | VRAM（L4 23.7GB で本走可か） |
|---|---|---|---|---|
| 0.6B | 6.795 s（**実測**） | **0.578 GPU時間** | ― | 余裕（読込 0.85GB） |
| 1.7B | ~19 s | ~1.6 GPU時間 | ~1.1–2.1 | 余裕 |
| 4B | ~45 s | ~3.8 GPU時間 | ~2.7–5.0 | 余裕 |
| 8B | ~91 s | ~7.6 GPU時間 | ~5.3–9.9 | **可**（4-bit 重み~4GB＋活性化。活性化が逼迫すれば batch1＋grad_accum16 で実効16維持＝計算ほぼ不変）。機種変更は不要の見込み |

**ラダー 1 周（各 1 run）合計 ≈ 0.58 + 1.6 + 3.8 + 7.6 ≈ 13.6 GPU時間。**

## 4. 総予算の式と規模配分 v1.x への含意

```
総予算 = Σ_model ( t_run(model) × run数(model) )
run数(model) = 軌道本数 × 群数(G_base, G+, …) × seed数      ← (A)図解設計で凍結（未確定）
```

- **run数が予算を支配する。** 例：5 seed × 2 群 × 数条件 ⇒ run数 ~10–30/model。すると **8B 単独で 76–230 GPU時間**に達する
  ―― ここで懐が縛る。1step の外挿帯（±0.3）より、**run数の設計（seed×群×条件）の方が予算への梃子が圧倒的に大きい**。
- **含意（規模配分 v1.x 素案）：**
  1. **0.6B→1.7B で「形」を固め**（プローブ妥当性・S(0)>0・SNR・CI 幅・seed 分散を安く決める）、
     **4B/8B は run数を絞って確証用**に回す（全 seed×群を大型で回さない）。
  2. **各規模で本走前に短パイロット**（30step 程度）で実測 t_run に置換 ―― 外挿帯を実測で潰してから run数を確定。
  3. **8B は L4 で可**。機種を上げる前に、活性化逼迫時は batch1＋grad_accum で実効batchを保つ（計算ほぼ不変・予算中立）。

## 5. 射程の棘（誇張しないために）

- **単一錨からの 13× 外挿**。1.7/4/8B の t_run は未測定。中心値は確定値でなく plan 値。各規模で実測置換が前提。
- **300step は設計値**（run 長）。t_run は step 数に線形ゆえ、本物の DPO 収束步数が決まれば再スケールする。
- **GPU時間 → Colab 計算ユニットの換算はしていない** ―― units/hour を実測していないため。
  必要なら次走で本セッションのユニット消費を実測して換算する（憶測で換算しない）。
- 本ノートは台帳 #10 の **run数前段**（モデル別 t_run の相対地形）を与えるに留まり、**run数自体は (A)/規模凍結を待つ**。
  予算 #10 の最終確定 = 実測 t_run（各規模）× 凍結 run数。
